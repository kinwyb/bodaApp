# 表格列定义用法（AppColumnDef / buildColumns）

> 代码路径：`src/components/grid-table/columnBuilder.ts`
> 基准版本：`main`（2026-10-20，`mergeCell` 提为一级属性后）
> 说明：本文只讲**怎么用**与**合并规则**。实现细节看 `columnBuilder.ts` 里的注释。

---

## 一、一句话结论

列定义只做三件事：**用 `dataType` 声明它是什么**，需要时覆盖 `fieldFormat`（显示值）、叠加 `style`（样式），最后交给 `buildColumns`：

```tsx
const columns = useMemo(() => buildColumns(COLUMNS), []);

<GridTable columns={columns} records={rows} />
```

三条铁律：

| 属性 | 语义 | 与默认值的关系 |
|---|---|---|
| `fieldFormat` | 单元格**显示什么** | **替换**（写了就不再用 dataType 的默认格式） |
| `style` | 单元格**长什么样** | **合并**（默认样式打底，同名字段以你为准） |
| `columnProps` | @visactor/vtable 其它列配置的兜底口子 | **整体覆盖**（不合并，不推荐再往里写 style / fieldFormat） |

---

## 二、导入

```ts
// 函数 + 类型都从子路径导入（index.ts 只导出组件与类型，原因见该文件注释）
import { buildColumns, type AppColumnDef } from '@/components/grid-table/columnBuilder';
```

`COLUMNS` 建议写成模块级常量（`AppColumnDef[]`），需要按业务动态增减时再在页面里拼。

## 三、`AppColumnDef` 字段表

| 字段 | 类型 | 说明 |
|---|---|---|
| `field` | `string` | 数据字段名，**必填** |
| `title` | `string` | 列标题，**必填** |
| `width` | `number` | 列宽（px），不传由 @visactor/vtable 分配 |
| `dataType` | `'text' \| 'number' \| 'date' \| 'datetime' \| 'boolean' \| 'tag'` | 决定控件、默认格式与对齐，默认 `text` |
| `precision` | `number` | 只对 `number`：小数位，`0` 表示整数 |
| `tagMap` | `Record<string, string \| { label, color }>` | 只对 `tag`：值 → 文案（可带文字颜色） |
| `booleanText` | `[string, string]` | 只对 `boolean`：勾选框右侧文案，顺序是 **[选中, 未选中]** |
| `sortable` | `boolean` | 列头显示排序（具体排序行为由表格的排序配置决定） |
| `fieldFormat` | `AppColumnFieldFormat` | 显示格式，覆盖 dataType 默认 |
| `style` | `AppColumnStyle` | 单元格样式，对象或函数，与默认样式合并 |
| `mergeCell` | `boolean \| 回调` | 单列纵向合并（@visactor/vtable 原生），详见第十四节 |
| `aggregate` | `'sum' \| 'count' \| 'distinct' \| 'avg' \| 'max' \| 'min' \| 'first'` | 默认汇总方式：配了它，底部统计行与分组组行都自动算，详见第十五节 |
| `group` | `boolean` | 默认按这一列分组（FilterTable），多列都标了按列顺序分层，详见 15.6 |
| `columnProps` | `Record<string, unknown>` | 透传 @visactor/vtable 其它列配置，最后执行、整体覆盖 |

## 四、`dataType` 速查

| dataType | 渲染 | 默认 fieldFormat | 默认 style |
|---|---|---|---|
| `text` | 文本 | 无（原始值） | 无 |
| `number` | 文本 | 有 `precision` 时 `toFixed(precision)`，否则原始值 | `{ textAlign: 'right' }` |
| `date` | 文本 | `formatDate()` → `YYYY-MM-DD`，空值 / `0001-01-01` 占位显示空串 | 无 |
| `datetime` | 文本 | `formatDateTime()` → `YYYY-MM-DD HH:mm:ss`，空值同上 | 无 |
| `boolean` | **只读**勾选框（`disable: true`） | 返回 `{ checked, disable, text? }` | 函数：居中 + 白底 + 只读复选框配色 |
| `tag` | 文本 | 按 `tagMap` 映射文案（没配的显示原值） | 函数：按值映射文字颜色 |

```ts
const COLUMNS: AppColumnDef[] = [
  { field: 'StyleCode', title: '款号', width: 110 },                                 // text
  { field: 'Qty', title: '总数量', width: 90, dataType: 'number', sortable: true },   // 右对齐
  { field: 'Rate', title: '达成率', width: 90, dataType: 'number', precision: 2 },     // 两位小数
  { field: 'YPDate', title: '预订日期', width: 100, dataType: 'date' },
  { field: 'CreateTime', title: '创建时间', width: 150, dataType: 'datetime' },
  { field: 'SSStep', title: '产能阶段', width: 100, dataType: 'boolean' },             // 只有勾选框
  // 勾选框右侧带文案
  { field: 'QMStep', title: '全码样阶段', width: 120, dataType: 'boolean', booleanText: ['已排产', '未排产'] },
  {
    field: 'State', title: '状态', width: 90, dataType: 'tag',
    // 字符串简写 = 只有文案；对象写法才指定颜色
    tagMap: { 1: '待审核', 2: { label: '已通过', color: '#389e0d' } },
  },
];
```

> `tagMap` 的键最终按 `String(value)` 匹配，对象字面量的数字键本身就是字符串，所以 `{ 1: '待审核' }` 能匹配数据里的 `1`。

## 五、`fieldFormat`：覆盖显示值

写了就**不再用** dataType 的默认格式。返回值是什么就显示什么。

```ts
// 1) 加单位
{ field: 'Qty', title: '数量', dataType: 'number', fieldFormat: (r) => `${r.Qty} 件` }

// 2) 换日期粒度（date 默认到日，这里只要年月）
{ field: 'YPDate', title: '预订月份', dataType: 'date',
  fieldFormat: (r) => String(r.YPDate ?? '').slice(0, 7) }

// 3) 空值 / 0 显示成占位符（比满屏 0 好读）
{ field: 'MWeight', title: '克重', dataType: 'number',
  fieldFormat: (r) => (Number(r.MWeight) > 0 ? r.MWeight : '-') }

// 4) 码表转中文（参数是 any，可以标成具体行类型）
{ field: 'KnitOrgID', title: '织造产地', width: 90,
  fieldFormat: (record: YupaiOrder) => ORG_NAME(record.KnitOrgID) }
```

签名（@visactor/vtable 的 `FieldGetter`）：

```ts
(record: any, col?: number, row?: number, table?: BaseTableAPI) => any
```

也支持 `{ get, set }` 形态（`FieldAssessor`），业务里暂时没用到。

**注意**：`fieldFormat` 只影响显示。要参与条件判断、提交给后端的，仍然是行数据里的原值。

## 六、`style`：对象与函数

### 6.1 传对象（静态样式）

```ts
// number 默认右对齐，这里加底色与加粗，对齐不受影响
{ field: 'Qty', title: '总数量', width: 90, dataType: 'number',
  style: { bgColor: '#fffbe6', fontWeight: 'bold' } }

{ field: 'Memo', title: '备注', width: 190,
  style: { color: '#8c8c8c', fontStyle: 'italic' } }
```

### 6.2 传函数（按行 / 按值算）

参数是 `StylePropertyFunctionArg`：

```ts
{
  row: number;               // 表格行号（含表头，业务行号 = row - table.columnHeaderLevelCount）
  col: number;
  table: BaseTableAPI;
  value?: FieldData;
  dataValue?: FieldData;     // 当前单元格的数据值
  percentile?: number;
  cellHeaderPaths?: ICellHeaderPaths;
}
```

```ts
{
  field: 'XDRate', title: '下单把握度', width: 100, dataType: 'number',
  style: ({ dataValue, row }) => ({
    ...(Number(dataValue) < 60 ? { color: '#cf1322' } : {}),   // 低于 60 标红
    bgColor: row % 2 ? '#fafafa' : '#ffffff',                  // 斑马纹
  }),
}
```

### 6.3 与默认样式合并（重点）

`style` **不是整份替换**，而是「默认样式打底、你的覆盖同名项」：

| 列定义 | dataType 默认 | 实际生效 |
|---|---|---|
| `number` + `style: { bgColor: '#eee' }` | `{ textAlign: 'right' }` | `{ textAlign: 'right', bgColor: '#eee' }` |
| `tag` + `style: { fontWeight: 'bold' }` | 函数（按值上色） | 函数：先按值上色，再叠 `fontWeight` |
| `boolean` + `style: { bgColor }` | 函数（居中 + 只读框） | 居中、只读框保留，底色被覆盖 |
| 只写 `columnProps.style` | — | 整份替换（不合并，见第八节） |

实现上：两边都是对象时浅合并；有一边是函数时包一层，先算默认再叠自定义。所以给 `tag` 列加个字重，不会把按值上色顶掉。

### 6.4 与 `cellStyle` / 统计行的关系

`GridTable` 组件内部会再包一层（`GridTable.tsx` 的 `decorate`）：把列的 `style` 作为 `base`，然后**按顺序短路**：

```
base = 列的 style（对象或函数的结果）
├─ 统计行        → 叠加灰底加粗后直接返回（不再往下走）
├─ 展开行        → 叠加"内容贴顶"的内边距后直接返回
└─ 页面 cellStyle → 有返回就叠加（语义化字段翻译后覆盖 base）
```

所以：统计行和展开行的样式由框架接管，页面 `cellStyle` 在那两种行上不生效。页面级「某行某字段提醒」用 `cellStyle` prop 更合适，列 `style` 只表达这列的固有样式。

## 七、`boolean` 与 `tag` 专项

### 7.1 自定义勾选框外观

```ts
{
  field: 'SSStep', title: '产能阶段', width: 110, dataType: 'boolean',
  booleanText: ['已排产', '未排产'],
  style: ({ dataValue }) => ({
    bgColor: Number(dataValue) === 1 ? '#f6ffed' : '#ffffff',
    // checkboxStyle 能直接写，AppColumnStyle 已并入 @visactor/vtable 的 CheckboxStyleOption
    checkboxStyle: { checkedFill: '#52c41a', checkedStroke: '#52c41a', size: 14 },
  }),
}
```

常用 `checkboxStyle` 字段：`defaultFill` / `defaultStroke` / `checkedFill` / `checkedStroke` / `disableFill` / `disableStroke` / `disableCheckedFill` / `disableCheckedStroke` / `size` / `spaceBetweenTextAndIcon`。

`dataType: 'boolean'` 的勾选框是**只读展示**（`disable: () => true`）。要能编辑，走可编辑表格（`editableFields` + 编辑器），别指望点这个框。

### 7.2 `tag` 配颜色

```ts
{ field: 'State', title: '状态', dataType: 'tag',
  tagMap: { 1: '待审核', 2: { label: '已通过', color: '#389e0d' } },
  style: { fontWeight: 'bold' } }   // 颜色按 tagMap 逐值走，字重来自这里
```

没配 `color` 的项**不返回 color**，文字沿用主题默认色（和底色自然一致，不写死黑/白）。

## 八、`columnProps`：兜底口子

`columnProps` 直接展开进 @visactor/vtable 的列配置，位于最后 —— **整体覆盖，不合并**。用于 `AppColumnDef` 没抽象的一级属性：

```ts
{
  field: 'OrderCode', title: '订单号', width: 130,
  columnProps: { headerStyle: { bgColor: '#fafafa', fontWeight: 'bold' } },
}
```

常见可用项：`headerStyle`（表头样式）、`cellType`（非 text/checkbox 的单元格类型）、`editor`、`tree`、`hide`、`disableColumnResize` 等，完整清单看 `ColumnsDefine`。（`mergeCell` 已提为一级属性，别再写这里。）

**别再往 `columnProps` 里写 `style` / `fieldFormat`**：写了就是整份替换，默认右对齐、只读框样式会一起丢。全仓库已无这种写法。

---

## 九、批量生成列

尺码这种重复结构用 `map` 生成：

```ts
const SIZES: AppColumnDef[] = ['S', 'M', 'L', 'XL'].map((title, index) => ({
  field: `Size${index + 1}`,
  title,
  width: 70,
  dataType: 'number' as const,     // ⚠️ 不加 as const 会被推成 string
  style: { bgColor: '#fafafa' },
  fieldFormat: (r: Record<string, unknown>) => {
    const value = Number(r[`Size${index + 1}`]);
    return value > 0 ? value : '';
  },
}));
```

## 十、覆盖优先级

从低到高：

```
① base（field / title / width / sortable）
② dataType 推导（style / fieldFormat / cellType / checked / disable）
③ def.fieldFormat（替换）        def.style（合并进 ②）        def.mergeCell（原样透传）
④ columnProps（整体覆盖 ①②③）
⑤ GridTable 运行时装饰（统计行 / 展开行短路优先，其后才是页面 cellStyle）
```

放一张对照：

| 你写了 | 结果 |
|---|---|
| `dataType: 'number'` 且 `fieldFormat` | 用你的格式，右对齐仍保留 |
| `dataType: 'number'` 且 `style: { bgColor }` | 右对齐 + 你的底色 |
| `dataType: 'tag'` 且 `style: { fontWeight }` | 按值上色 + 你的字重 |
| `style` 且 `columnProps.style` | 只用 `columnProps.style` |
| `fieldFormat` 且 `columnProps.fieldFormat` | 只用 `columnProps.fieldFormat` |

## 十一、类型是怎么来的

```ts
// 显示值类型：从文本列的 fieldFormat 属性反查，再剥掉可选带来的 undefined
export type AppColumnFieldFormat = NonNullable<TextColumnDefine['fieldFormat']>;
//   = FieldGetter | FieldAssessor
//   = ((record, col?, row?, table?) => any) | { get: FieldGetter; set: FieldSetter }

// 样式类型：文本列的 style（对象或函数）+ 复选框列专有的 checkboxStyle
export type AppColumnStyle =
  | NonNullable<TextColumnDefine['style']>   // ITextStyleOption | ((args: StylePropertyFunctionArg) => ITextStyleOption)
  | TYPES.CheckboxStyleOption                // 含 checkboxStyle / size 等
  | ((args: TYPES.StylePropertyFunctionArg) => TYPES.ITextStyleOption | TYPES.CheckboxStyleOption);
```

- `NonNullable<T>` 是必要的：`fieldFormat?: X` 本身隐含 `undefined`，不剥掉的话把该类型当「值类型」用（参数标注、`Record<string, AppColumnFieldFormat>`）时处处要补 `| undefined`。
- 之所以从 `TextColumnDefine` 取而不直接用 `TYPES.FieldFormat`：两者**完全等价**（已用 TS 编译器 API 验证），取列属性是为了「跟列定义同源」，将来 @visactor/vtable 调整该属性类型时自动跟随。想更直白也可以改成 `TYPES.FieldFormat`。
- number / date / datetime / tag 最终都由文本单元渲染，boolean 是 checkbox 单元，两者都 `extends IBasicColumnBodyDefine`，`fieldFormat` 同源，所以用文本列当基准覆盖全部 `dataType`。

## 十二、踩坑清单

1. **`map` 生成列必须 `dataType: 'number' as const`**，否则字面量被放宽成 `string`，类型检查不过。
2. **`style` 不要写进 `columnProps`**：那是整份替换，默认对齐 / 只读复选框样式会丢；直接写一级 `style` 才会合并。
3. **`booleanText` 顺序是 `[选中, 未选中]`**，写反了文案不会报错，只是显示颠倒。
4. **`precision: 0` 有效**（内部用 `!== undefined` 判断），想要整数显示就显式写 0，别指望默认。
5. **页面里的 `columns` 要稳定引用**（模块级常量或 `useMemo`）：`GridTable` 内部 `finalColumns` 依赖 `columns` 引用，每次渲染新建数组会让它重新装饰列并 `updateOption` 空转。
6. **`tagMap` 的键按 `String(value ?? '')` 查**：`{ 1: 'x' }` 与 `{ '1': 'x' }` 等价、布尔值也能命中；但空值统一折成 `''`，所以配 `undefined` / `null` 键永远不会命中，要配空字符串键（`{ '': '未设置' }`）。
7. **`fieldFormat` 只管显示**：排序、校验、提交都用行数据原值，别把业务逻辑塞进格式函数里做副作用。
8. **给 `date` / `datetime` 列自定义 `fieldFormat` 就绕开了默认格式化**：后端用 `0001-01-01` 表示空日期，这时要自己挡（判断 `startsWith(EMPTY_DATE_PREFIX)`），否则会把占位日期显示出来。
9. **合并有两条路，别混用**：列级 `mergeCell` 只管「本列相邻是否合并」，分组合并用表格的 `mergeGroups`；两者都只认同组**相邻**行——同组记录被别的行隔开就会切成多个小块，要连成整块需把分组字段排到 `ORDER BY` 最前（见第十四节）。

## 十三、完整示例（预订单列表）

```ts
import type { AppColumnDef } from '@/components/grid-table/columnBuilder';
import { type YupaiOrder, YupaiMachineSizeHeader } from '@/api';
import { ORG_NAME } from '@/store/orgs.ts';

export const COLUMNS: AppColumnDef[] = [
  { field: 'WorkPlace', title: '产地', width: 90 },
  { field: 'YPDate', title: '预订日期', width: 100, dataType: 'date', sortable: true },
  // 码表转中文：只覆盖显示，排序仍按 ID
  { field: 'KnitOrgID', title: '织造产地', width: 90,
    fieldFormat: (record: YupaiOrder) => ORG_NAME(record.KnitOrgID) },
  { field: 'Qty', title: '总数量', width: 90, dataType: 'number', sortable: true },
  // 纯样式：number 的右对齐保留
  { field: 'XDRate', title: '下单把握度', width: 95, style: { textAlign: 'right' } },
  // 阶段列
  { field: 'SSStep', title: '产能阶段', width: 100, dataType: 'boolean' },
  { field: 'QMStep', title: '全码样阶段', width: 110, dataType: 'boolean' },
  // 批量尺码列：0 与空值都不显示（number 默认右对齐，不用再写 style）
  ...YupaiMachineSizeHeader.map((title, index) => ({
    field: `MCSize${index + 1}`,
    title,
    width: 82,
    dataType: 'number' as const,
    fieldFormat: (record: YupaiOrder) => {
      const value = record[`MCSize${index + 1}`];
      return value === null || value === undefined || value === '' ? '' : Number(value) > 0 ? value : '';
    },
  })),
];
```

对应的详情表格（可编辑）只需在列定义外挂 `editableFields`，列本身仍然只声明「展示成什么」（完整实现在 `V0280/models/yupaiOrderEditColumns.ts`）：

```tsx
const columns = useMemo(() => buildColumns(DETAIL_COLUMNS), []);

<GridTable columns={columns} records={rows} editableFields={DETAIL_EDITOR_FIELDS} />
```

## 十四、合并单元格

只作用于**表头以下、纵向相邻**的行。表头合并是另一套机制（`columns` 嵌套分组），与本节无关。

### 14.1 两条路，别混用

| 写法 | 位置 | 能力 | 适用 |
|---|---|---|---|
| `mergeCell: true / false / 回调` | **列定义**（`AppColumnDef`） | 只判断「本列相邻两行是否合并」，原生语义 | 单列按显示值合并 |
| `mergeGroups={{ topMergeColumn, mergeColumnSort }}` | **表格属性**（`GridTable` / `FilterTable`） | 门槛列 + 顺序列层级、跨列联动 | 分组表头式合并（产地→款号→尺码） |

```tsx
// 单列：显示值相同就合并
const COLUMNS: AppColumnDef[] = [
  { field: 'Memo', title: '备注', mergeCell: true },

// 分组合并：表级一次配好，所有声明的列一起生效
<FilterTable
  columns={buildColumns(COLUMNS)}
  records={dataSource}
  mergeGroups={{
    topMergeColumn: ['OrderCode'],                          // 无论合并哪列，先要求同一订单
    mergeColumnSort: ['WorkPlace', 'StyleCode', 'SizeName'], // 层级：产地 → 款号 → 尺码
  }}
/>
```

⚠️ 同一张表里不要既写列级 `mergeCell` 又配 `mergeGroups`：两套机制都会向 @visactor/vtable 报合并范围，容易互相覆盖。

### 14.2 两个参数怎么分工

| 参数 | 作用 | 参与「按顺序逐列判断」 |
|---|---|---|
| `mergeColumnSort` | 真正要按顺序合并的列。**顺序即层级**（粗 → 细），**只有这里列出的列才会被合并** | **是**，顺序很关键 |
| `topMergeColumn` | 前置门槛列 / 上级分组列：值必须**全部相同**，才允许继续考虑后面的合并 | **否**，只是所有合并前的强制条件 |

判定「当前列能否合并」时，取的是**门槛列全集 + 顺序列前缀**，逐一相等才算通过：

```ts
// 产地列：OrderCode + WorkPlace
// 款号列：OrderCode + WorkPlace + StyleCode
// 尺码列：OrderCode + WorkPlace + StyleCode + SizeName
// 未在顺序数组里的列：不合并
```

要点：

- **当前列是谁由表格在运行期判断**（按 `getBodyColumnDefine(col,row).field` 反查），所以一份配置覆盖多列，各列自动取不同前缀；
- `topMergeColumn` 与 `mergeColumnSort` 重叠只会比一次（同一字段重复比较无副作用）；
- 前缀按**数组顺序**取，不是按列在表格里的左右顺序 —— 两者保持一致最省心（数组就照列的先后写）。

### 14.3 实现：为什么走 `customMergeCell`

`mergeGroups` 不是把条件塞进列级 `mergeCell` 回调，而是预扫描数据、建索引，再以 @visactor/vtable 的 `customMergeCell` 返回矩形范围：

```
buildMergeGroupIndex(rows, config)          // O(列数 × 行数 × 字段数)，只跑一次
  → Map<字段, 行号 → {start, end}>
  → customMergeCell(col, row, table)        // 每格 O(1) 查表
```

对比列级 `mergeCell` 回调：那个是**每格**都从当前行向上向下扫整列（`_cellRangeMap` 只缓存同格结果），整体是 `O(行数²)`；数据上万行时卡顿明显。

索引由 `GridTable` 组件负责重建：

| 变化 | 处理 |
|---|---|
| 表头排序 | 排序在 React 层完成（`rows` 是排序后的数组），索引跟着 `useMemo` 自动重建 |
| 换数据 / 翻页 / 搜索 | 同上，`rows` 引用变即重建 |
| 统计行 | 建索引前先剔除（否则最后一块会把统计行吞进去） |

### 14.4 判断顺序与值语义

`buildMergeGroupIndex` 建索引时按顺序短路，**三步都过才合并**：

1. **本列显示值相同** —— 顺序列前缀里含本列，天然满足；门槛列不含本列时靠这一条兜底；
2. **两行都取得到原始记录** —— 统计行、空补足行不在索引里，一律断开；
3. **门槛列全部相同 + 顺序列前缀全部相同** —— 字段名在两行上都必须存在，写错字段名判为不相等（方向安全，不会放大合并范围）。

值比较的语义：

| 情况 | 结果 |
|---|---|
| 两边都为空（`null` / `undefined` / `''`） | 相等 |
| 一边空一边有值 | 不相等 |
| `1` 与 `'1'` | 相等（按字符串比，避开 SQL 直查的 number/string 漂移） |
| `'abc'` 与 `'ABC'` | 不相等（不做大小写折叠） |

### 14.5 两个硬前提

**① 合并只认同组相邻行 —— 想要连成一块就得排好序。** 分组是「遇到不相等就断开」，不是全局找同值。同一组记录被别的行隔开，就会被切成多个小块。这不一定是坏事：像 V0281 变更明细以「修改时间」为主序，同订单的变更本来就被时间打散，得到零星小块正是业务上想要的样子；要连成整块才需要把分组字段排到 `ORDER BY` 最前面。

**② 判断依据只能取自行上的字段。** 这是 @visactor/vtable 两套合并机制共同的前提（内部都是「与相邻行比较」），写成链式规则（如「与上一行相差 3 秒内」）会导致块边界不稳定。

### 14.6 已知副作用

| 行为 | 表现 |
|---|---|
| 编辑 | 编辑一个合并格会**写回整段**（`range.start.row` ~ `range.end.row` 逐行改值），明细表慎用 |
| 复制 / 导出 | 只认合并区起点，其余位置是空串 |
| 行高 | 合并格高度 = 被合并各行高度之和，内容多少不影响 |
| 取显示值 | 实现里用 `getCellValue(col, row, true)`，**第三参数必须传**：否则 `getCellValue → getCustomMerge → 回调` 无限递归 |
| 范围生命周期 | `customMergeCell` 的结果**不参与** @visactor/vtable 的 `_cellRangeMap` 缓存，索引必须自己维护（组件已处理） |

### 14.7 使用清单（照这个对一遍就不会踩）

| # | 注意点 | 后果 / 做法 |
|---|---|---|
| 1 | **想要「同组连成一块」，`ORDER BY` 就得按分组字段排** | 按业务主序排（如 V0281 按修改时间倒序）时同组记录会被打散，得到的是多个小块 —— 这是预期行为，不是 bug。要整块就 `ORDER BY OrderCode, WorkPlace, …`；要业务可读性就保留 `ChangeTime DESC`，接受碎块 |
| 2 | **注意表头排序会重排数据** | 按「分组字段的前缀」排序（如按 `OrderCode`）同组仍相邻，合并照旧；按其它列（如数量）排就会打散同组、合并消失。介意的话给这些列 `sortable: false` |
| 3 | **`mergeGroups` 写成模块级常量** | 内联 `mergeGroups={{…}}` 每次渲染都是新对象，会重算一遍索引；数据大时肉眼可见卡顿 |
| 4 | **字段名是数据字段，不是列标题** | `mergeColumnSort: ['款号']` 不会报错，只是静默不合并。用 `StyleCode` 这种真实 `field` |
| 5 | **门槛列不必显示成列** | `topMergeColumn: ['YupaiOrderID']` 完全可以，只要行数据上有这个字段 |
| 6 | **未声明进 `mergeColumnSort` 的列不会合并** | 想让订单号也合并，把它放进数组（通常是第一位） |
| 7 | **合并块的样式 / 颜色取「块首行」** | 斑马纹、按行标色在合并块里统一成首行那一条；按行判断的 `cellStyle` 不要指望在块内分段生效 |
| 8 | **分页只在页内合并** | 后端分页时每页独立建索引，跨页不会连成一块 |
| 9 | **可编辑表格慎用** | 编辑合并格会写回整段（14.6），明细表建议只读展示时用 |
| 10 | **别和行展开（`expandable`）同用** | 合并块会跨过展开区，块内文字被整体拉高居中，观感很怪 |
| 11 | **别在同一列同时写 `mergeCell` 和 `mergeGroups`** | 两套机制各自向 @visactor/vtable 报范围，行为不可预期 |
| 12 | **整列为空会并成一整块空白** | 空值两边算相等，若整列都是空且分组条件一致，会出现一大片空块 —— 不想这样就把该列从 `mergeColumnSort` 里去掉 |

## 十五、默认汇总（列上的 `aggregate`）

### 15.1 一句话

列上写 `aggregate: 'sum'`，**页面就不用再算汇总**：底部统计行和分组组行都会按这个配置自动算。

```ts
const COLUMNS: AppColumnDef[] = [
  { field: 'OrderCode', title: '订单号', width: 120, aggregate: 'count' },   // 条数
  { field: 'Qty',       title: '款式数量', width: 100, dataType: 'number', aggregate: 'sum' },
  { field: 'Hours',     title: '工时',     width: 90,  dataType: 'number', aggregate: 'sum' },
  { field: 'Customer',  title: '客户',     width: 90,  aggregate: 'first' }, // 取首条
];

<GridTable columns={buildColumns(COLUMNS)} records={rows} />   // 底部自动出「合计」行
```

### 15.2 三种生效场景

| 页面怎么配 | 结果 |
| --- | --- |
| 只配列 `aggregate`，不传 `summary` | 自动生成底部统计行（最后一格都按列配置算） |
| 配了 `group` 但没写 `group.aggregates` | 组行自动继承列上的 `aggregate` |
| 传了 `summary` / `group.aggregates` | **以显式配置为准**，列的 `aggregate` 只用于没被覆盖的场景 |

显式写 `group.aggregates: []`（空数组）表示「组行不要任何汇总」，不会回退去继承列配置。

### 15.3 七种汇总方式

| `aggregate` | 含义 | 备注 |
| --- | --- | --- |
| `sum` | 求和 | 数值按 `toNumberOrZero` 转，空值算 0 |
| `count` | 条数 | 明细行数，不看字段值 |
| `distinct` | 去重计数 | 忽略空值；`1` 与 `'1'` 视为同值 |
| `avg` | 平均 | 空组返回 0，不四舍五入（小数位交给列的 `precision`） |
| `max` / `min` | 最大 / 最小 | 空值算 0 参与比较 |
| `first` | 取首条明细的值 | 适合「组内都相同」的字段（客户、业务员） |

### 15.4 与手写 `summary` 的关系

`summary` 是**整行数据**（页面自己算好的一整条 record），`aggregate` 是**单个字段怎么算**。
两者不冲突：手写的 `summary` 一旦传了，就整行接管，自动汇总不再介入。

需要「大部分列自动、个别列手写」时，仍然用手写 `summary`（把自动的部分自己算进去），
或者用 `group.aggregates` 里的自定义函数（见 `group.ts` 的 `GroupAggregate.aggregate`）。

### 15.5 注意点

| # | 注意点 | 后果 / 做法 |
|---|---|---|
| 1 | **空表不生成统计行** | 否则「暂无数据」下面会多一行 0。数据回来后自动出现 |
| 2 | **同一个字段配多次只取第一次** | 汇总结果写在同名字段上，重复配置没有意义 |
| 3 | **统计行只算明细，不算组行** | 分组场景下先拍平到明细再算，所以不会重复计数 |
| 4 | **分组字段列不要配 `aggregate`** | 它的值是组标题字符串，求和/平均没有意义 |
| 5 | **文本列配 `first` 才有意义** | 配 `sum` 会得到 0（非数字一律当 0），看起来像「没生效」 |
| 6 | **别叫 `aggregation`** | 那是 @visactor/vtable 原生字段（表格自带的合计行），语义不同，混用会互相覆盖 |

### 15.6 默认分组（`group: true`）

列上写 `group: true`，表格**一进来就是分组状态**，用户不用每次手动点：

```ts
const COLUMNS: AppColumnDef[] = [
  { field: 'Month',    title: '生产月份', width: 130, group: true },
  { field: 'Customer', title: '客户',     width: 90,  group: true },  // 第二层
  { field: 'Qty',      title: '款式数量', dataType: 'number', aggregate: 'sum' },
];

<FilterTable columns={buildColumns(COLUMNS)} records={rows} groupable />
```

- **多列都标了**，按列定义里的**先后顺序**由外到内分层（月份 → 客户 → 明细）。
- 组行标题**只显示值本身**（`2023-12`），不加「生产月份:」前缀 —— 值就在这一列下面，
  加前缀是重复，还容易被列宽截断。
- `groupable` 与 `group` 是两件事：
  - `group: true` = 默认就分组（**不需要** `groupable`）；
  - `groupable` = 显示那个「分组」按钮让人改（即使一列都没标 `group` 也有面板）。
  - 只标 `group` 不开 `groupable`：默认分组、用户改不了；两个都开：默认分组 + 可调整。
- 用户手动改过之后，即使 `columns` 重新生成也不会覆盖他的选择（内部用 dirty 标记）。
