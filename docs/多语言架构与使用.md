# 多语言架构与使用

> 本文介绍当前 React 客户端的 i18n 架构、资源组织、页面接入方式、旧系统菜单迁移，
> 以及 Agent 和 HTTP 请求如何携带界面语言。

---

## 一、设计结论

当前方案采用：

```text
中文原文作为 source key
  + 按页面 View code 覆盖
  + 独立菜单翻译 menu.ts
  + 缺失翻译回退中文
  + 构建期静态资源
  + React 内动态切换，不刷新页面
```

支持语言：

| 语言 | locale |
|---|---|
| 中文 | `zh-CN` |
| 英文 | `en-US` |
| 越南文 | `vi-VN` |

核心原则：

1. 代码里直接写中文 source，例如 `t('保存')`，不从英文语义 key 反查中文。
2. 缺少目标语言翻译时直接返回中文，不显示空白或 key。
3. 机器标识不翻译，包括 `view`、`field`、`action.id`、参数名、后端业务值。
4. 菜单属于公共导航，单独放在 `menu.ts`。
5. 页面文案按页面 code 自动继承，不要求每条 `t()` 手写 scope。
6. 切换语言不整页刷新，不丢失当前页签、表格和表单状态。
7. 当前没有线上翻译下载，也没有缺失 key 自动上传。

## 三、翻译查找顺序

### 3.1 普通页面文案

当页面包裹在 `PageLocaleProvider` 中时，`t('中文')` 按以下顺序查找：

```text
当前页面 code
  -> 父级页面 code
  -> common
  -> 中文原文
```

例如页面 `V0189_V0279_V0280`：

```text
V0189_V0279_V0280
  -> V0189_V0279
  -> V0189
  -> common
  -> 中文原文
```

父级 code 适合放多个页面共享的业务词条。

### 3.2 菜单文案

菜单使用独立作用域：

```ts
t('报表管理', { scope: 'menu' })
```

查找顺序：

```text
menu
  -> common
  -> 中文原文
```

侧栏、菜单搜索、页签标题、面包屑、Agent 导航标题和层级都使用 `menu` 作用域。

### 3.3 显式指定公共作用域

```ts
t('保存', { scope: 'common' })
```

只查 `common`，不查当前页面和父级页面。

## 四、运行时架构

### 4.1 locale 初始化

`src/i18n/index.ts` 按以下优先级确定初始语言：

```text
localStorage['bodaway.locale']
  > navigator.language
  > zh-CN
```

浏览器语言会映射到受支持的 locale：

```text
zh-* -> zh-CN
en-* -> en-US
vi-* -> vi-VN
```

`main.tsx` 在 React 挂载前调用 `initializeLocale()`，同步：

- 当前 i18n locale
- `document.documentElement.lang`
- dayjs locale

### 4.2 React Provider

`LocaleProvider` 负责：

- 当前 locale 状态
- antd / `@ant-design/x` locale
- 语言切换方法

`PageLocaleProvider` 负责绑定当前页面 View code。

`MainLayout` 渲染业务页面时自动包裹：

```tsx
<PageLocaleProvider code={meta.view}>
  <PageComponent ... />
</PageLocaleProvider>
```

页面通常不需要手动包 Provider。

### 4.3 动态切换

语言入口位于登录页右上角和主界面 Header；`LanguageSwitcher` 修改 locale 后：

- 写入 `localStorage`
- 更新 React locale context
- 更新 antd / X 组件语言
- 更新 dayjs locale
- 更新 `<html lang>`
- **不刷新页面**

因此当前页签、表单值、表格状态和未提交单据不会丢。

已经接入 `t()` 的界面会立即重渲染；尚未迁移的页面文案会继续显示中文，不会触发整页刷新。

### 4.4 组件库语言

antd 支持：

```text
zh_CN / en_US / vi_VN
```

`@ant-design/x` 当前只提供中文和英文 locale。越南文时：

```text
antd: vi_VN
@ant-design/x: en_US 兜底
业务文案: vi-VN
```

## 五、日常使用

### 5.1 普通组件

```tsx
import { useI18n } from '@/i18n/context';

export function SaveButton() {
  const { t } = useI18n();
  return <button>{t('保存')}</button>;
}
```

`useI18n()` 只使用公共作用域，不自动继承页面 code。

### 5.2 业务页面

页面顶层调用：

```tsx
import { usePageI18n } from '@/i18n/context';

const Page: React.FC<ViewPageProps> = ({ view }) => {
  const { t } = usePageI18n(view);

  return <Button>{t('查询')}</Button>;
};
```

即使 Provider 已经绑定 `view`，显式传入也便于静态阅读。

### 5.3 非组件模块

`columns.ts`、共享纯函数等模块不能直接使用 React Hook。优先把 `t` 作为参数传入：

```ts
import type { Translate } from '@/i18n';

export function buildColumns(t: Translate) {
  return [
    { field: 'ZZZZTotalNum', title: t('织造产量') },
  ];
}
```

页面：

```tsx
const columns = useMemo(
  () => buildColumns(t),
  [t],
);
```

### 5.4 变量插值

```ts
t('{year}第{week}周', {
  vars: {
    year: 2026,
    week: '03',
  },
});
```

中文回退时同样会插值：

```text
2026第03周
```

### 5.5 不翻译的内容

以下内容保持原值：

- View code
- 后端字段名
- `action.id`
- 请求参数名
- 组织 ID
- 物料、客户、订单等业务主数据
- 后端返回的业务枚举值

只翻译它们的标签和标题。

## 六、资源写法

### 6.1 common.ts

适合登录页、公共按钮、表格工具栏、Agent UI 等跨页面文案。

```ts
export default {
  保存: 'Save',
  查询: 'Query',
  暂无数据: 'No data',
};
```

缺少词条时回退中文。

### 6.2 menu.ts

菜单翻译只按后端 `DesktopMenu.MenuName` 查找：

```ts
export default {
  基础资料: 'Base Doc',
  计划管理: 'Program management',
  报表管理: 'Report Manager',
};
```

菜单名来自后端，不使用页面 code。

### 6.3 页面翻译

文件名必须是页面 View code：

```text
src/i18n/locales/en-US/pages/V0277_V0354.ts
```

内容只放该页面覆盖：

```ts
export default {
  查询: 'Search',
  周生产数据: 'Weekly production data',
};
```

父级目录可放共享词条：

```text
src/i18n/locales/en-US/pages/V0018.ts
```

由 `V0018_V0326`、`V0018_V0332`、`V0018_V0372` 共同继承。

## 七、菜单翻译迁移

菜单资源通过脚本从旧客户端生成：

```bash
npm run i18n:import-menu
```

默认读取：

```text
~/Downloads/BodaLanguage/Message.en-US.resx
~/Downloads/BodaLanguage/Message.vi-VN.resx
~/Downloads/Boda/bin/Debug/<locale>/Tr.resx
```

旧系统资源有两层：

```text
Message.*.resx
  -> 内置基础翻译
Tr.resx
  -> 运行时下载的覆盖翻译
```

因此迁移顺序是：

```text
Message
  -> Tr.resx 覆盖
  -> 新菜单补充词条
  -> 只保留当前 DesktopMenu 中存在的 MenuName
```

旧资源里有一部分值只是中文回填。生成脚本会使用
`SUPPLEMENTAL_MENU_TRANSLATIONS` 补齐当前菜单树缺失的英文和越南文。

以后新增菜单时：

1. 先把中文菜单名加入后端 `desktopMenu`。
2. 在 `scripts/import-legacy-menu-i18n.mjs` 的补充词条中加入英文、越南文。
3. 执行 `npm run i18n:import-menu`。
4. 执行 `npm run i18n:check`。

不要只手工改 `menu.ts`，因为下次重新生成会覆盖。

自定义路径：

```bash
LEGACY_BODA_ROOT=/path/to/Boda \
LEGACY_LANGUAGE_ROOT=/path/to/BodaLanguage \
npm run i18n:import-menu
```

## 八、新增页面接入步骤

1. 确认页面 View code，例如 `V0277_V0354`。
2. 页面入口使用 `usePageI18n(view)`。
3. JSX 文案改为 `t('中文')`。
4. 列定义、共享纯函数把 `t` 作为参数传入。
5. 在对应语言目录新建页面文件：

```text
src/i18n/locales/en-US/pages/V0277_V0354.ts
src/i18n/locales/vi-VN/pages/V0277_V0354.ts
```

6. 只翻译显示文案，不翻译字段名和业务值。
7. 执行 `npm run i18n:check`。
8. 执行 `npm run build` 和 `npm test`。

## 九、Agent 与 HTTP

### 9.1 chat.send

每次 `chat.send` 都在 metadata 中携带当前界面语言：

```json
{
  "metadata": {
    "locale": "en-US"
  }
}
```

带附件时：

```json
{
  "metadata": {
    "locale": "vi-VN",
    "attachments": [
      { "name": "a.pdf", "size": 1024 }
    ]
  }
}
```

以下发送路径都携带 locale：

- 用户正常发送
- 生成中的 steer
- 自动 UI 事件批次
- 失败重发

后端应把 `metadata.locale` 作为本轮默认回复语言，并允许用户明确要求切换回复语言。

### 9.2 Agent guide

以下内容继续使用中文，只维护一份：

- `description.md`
- `PAGE_GUIDE.summary`
- `PAGE_GUIDE.steps`
- `PAGE_GUIDE.terms`
- `PAGE_GUIDE.cautions`

这些是给模型看的内部上下文，不需要管理员逐语言维护。

页面中的按钮、列标题、字段 label 如果已经走 `t()`，会自然进入 Agent 快照；
`field`、action id、参数名仍保持机器标识。

### 9.3 HTTP

所有 HTTP 请求自动携带：

```http
Accept-Language: zh-CN
```

后端可据此本地化错误信息或枚举显示。

## 十、检查与验证

```bash
npm run i18n:check
npm run menu:descriptions:check
npm test
npm run build
```

`i18n:check` 检查：

- 页面 code 翻译目录是否仍对应真实页面目录。
- 当前每个菜单是否有 `menu.ts` 词条。
- `menu.ts` 是否包含已删除菜单。
- 中文 key 的翻译值是否仍然等于中文。
- `NC`、`APS` 这类不含中文的缩写允许原样。

当前菜单清单取自 `src/api/mock/data/power/desktopMenu.json`。生产菜单发生增删改时，
需要同步更新这份样例菜单，或调整检查脚本的数据来源，再重新生成 `menu.ts`。

当前没有：

- 启动时下载翻译
- 缺失 key 自动上报
- 翻译后台自动写入本地资源

如需线上热更新，后续应另加带版本号的 JSON overlay；缺失 key 上报建议仅在开发和测试环境开启。

## 十一、常见问题

### 菜单没翻译

检查：

1. `menu.ts` 是否有对应 `MenuName`。
2. 调用是否使用 `{ scope: 'menu' }`。
3. 新增菜单后是否执行了 `npm run i18n:import-menu`。
4. `npm run i18n:check` 是否通过。

### 页签或面包屑没翻译

它们也属于菜单上下文。页签标题必须使用：

```ts
t(meta.label, { scope: 'menu' })
```

面包屑使用同一 scope。

### 页面文案没翻译

检查：

1. 页面是否调用了 `usePageI18n(view)`。
2. 对应页面 code 文件是否存在。
3. 文案是否仍是硬编码中文，没有经过 `t()`。
4. 列定义是否把 `t` 传进了非组件模块。

### 切换语言后部分页面仍是中文

业务页面已经统一接入；若新增页面仍有中文，按“页面文案没翻译”逐项检查。
后端业务数据、用户姓名、客户/物料主数据不属于 UI 文案，不会被翻译。

### 修改中文 source key 后翻译失效

当前翻译以中文原文为 key。修改中文文案等同于新增 key，需要同步修改英文、越南文资源。
`i18n:check` 只能检查菜单；页面翻译建议在评审时一并检查。

## 十二、当前覆盖范围

```text
登录页
工作台 Dashboard
主界面菜单 / 页签 / 面包屑
GridTable 公共工具栏
src/pages/views 下全部业务页面
通用列表页 ViewPage
文件浏览面板
Agent 顶栏、欢迎页、输入区、会话列表
```

以下内容仍保持中文：

- `bridged.ts` 中的 Agent guide / terms / cautions
- `description.md`
- 后端业务数据和主数据
- 用户姓名、组织名称等运行时数据

页面文案批量维护命令：

```bash
npm run i18n:pages:extract
npm run i18n:pages:apply
npm run i18n:pages:generate
```

`i18n:pages:extract` 生成页面文案清单；`i18n:pages:apply` 将真实 UI 字符串包成 `t()`；
`i18n:pages:generate` 合并旧系统资源、补充词条和已有页面翻译，生成
`src/i18n/locales/<locale>/pages/<ViewCode>.ts`。

模块级列定义不要手工调用模块级 `t()`。列标题由 `GridTable` / `FilterTable`
在页面作用域内统一翻译，避免语言切换时冻结在模块加载时的文案。
